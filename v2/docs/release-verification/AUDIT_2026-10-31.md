## P0

### P0-1 · A stored TOTP seed reaches any agent, MCP client or CLI caller through `entry.reveal` / `credmgr_get` — reproduced

- **Where:** `v2/crates/brokerd/src/ops.rs:2444-2499` (`entry.reveal`) → `v2/crates/brokerd/src/entry_doc.rs:468-506`
  (`reveal_json` returns every field's `value`, with no `TotpSeed` filter); MCP `credmgr_get` → `entry.reveal`
  (`v2/crates/mcp/src/tools.rs:409-415`). The approval path (`ops.rs:620-711`) returns the same document, so a locked
  vault leaks it too once someone approves. `totp.seed` (`ops.rs:2646-2680`) refuses with `presence_required`, but it
  is not the only door: the `totp.code` comment at `ops.rs:2585-2592` itself says the raw entry value *is* the seed.
- **Reproduction** (`python3 -I $S/s1_totp_seed.py`, then `$S/s3_mcp_seed.py`): fresh vault, owner creates node `p`
  with workdir `W`, creates an entry whose only field is an `otpauth://…secret=…` URI, and a 3-field login entry whose
  third field is a bare base32 seed (it infers as `type: "totp-seed"`, `hasTotp: true`). Then a **tokenless** process
  with cwd `W` (default `agentAccess: read-write`):
  ```
  totp.seed   → {"error":"presence_required", ...}
  entry.reveal {node:p, entry:<otpauth entry>}   → contains the seed: True   field types: ['totp-seed']
  entry.reveal {node:p, entry:<login entry>}     → contains seed2: True
  credmgr mcp (cwd W): tools/call credmgr_get {node,entry}  → id 3: contains seed=True
  ```
- **Why it matters:** the seed/code split is the stated guarantee for stored 2FA: "An agent … cannot get the seed, so
  it cannot generate codes tomorrow … a leaked seed is worth forever" (`v2/docs/07_TWO_FACTOR.md:462-470`), and
  `totp.seed` is listed as presence-gated everywhere. In fact the seed needs no decision at all beyond the plain
  `reveal` an agent already has. False in the shipped documents: `v2/PRIVACY.md:155` ("it can get a 2FA code but never
  a 2FA seed (the MCP server has no tool for one, and the broker refuses the operation)"), `v2/docs/10_API_AND_MCP.md:513-515`
  ("No TOTP seed"), `v2/SECURITY.md:98` and `v2/README.md:136`/`v2/RELEASE.md:356` ("Revealing a TOTP seed … refused"),
  `07 §6` table row and `i13`/`phase5_totp_items.rs` coverage claims (they test the `totp.seed` op, not the seed).
  `SECURITY.md:34` lists "any way to obtain a stored 2FA seed rather than a generated code" as in scope — this is one.
- **Confidence:** high (reproduced on the real daemon and the real MCP server).

## P1

### P1-1 · An approval is consumed by whichever in-reach caller asks first, for every field — reproduced (K-7 (b) understates it)

- **Where:** `v2/crates/brokerd/src/state.rs:1739-1781` (`approval_for_reveal` finds the slot by `(node, entry)` only);
  `ops.rs:620-711` (`reveal_via_approval` hands the staged document to any caller whose scope would reveal the entry
  ignoring the lock, and narrows by *that caller's* `fieldIds`). `PendingApproval` carries no requester and no field list.
- **Reproduction** (`python3 -I $S/s2_approval.py`): node `p` (workdir `W`) and sub-node `s` under it (workdir `W/sub`);
  entry `DB` with fields `user`, `password`; owner locks the vault.
  ```
  A (tokenless, cwd W)  entry.reveal {fieldIds:[user]}  → approval_pending rq_da6c…
  vault.approval_get (tokenless, cwd /)                  → lists rq_da6c… with node P / entry DB (no field, no requester)
  vault.approval_decide {request, approved:true, passphrase}  → ok, authorisedBy factors
  B (a different tokenless process, cwd W/sub, scope s) entry.reveal {node:p, entry} (no fieldIds)
                                                         → got the approved value: True | keys ['entry','fields','node']
  A retries                                              → approval_pending rq_4547… (a new request)
  ```
- **Why it matters:** the person approved A's request for one field; B, which never asked and was never approved, got
  the whole entry (password included), and A was left with a fresh prompt. `07_TWO_FACTOR.md:374` says "The approval
  covers **one request**: one entry, once" — false. K-7 (b) (`PHASE8_AUDIT_REPORT.md:426`, bound at `:435`) discloses
  the keying but bounds it as "needs a same-user process that also **holds a token** able to ask for that entry"; no
  token is needed (cwd scoping suffices, including a sub-node's directory), and the field narrowing of the original
  request is not bound into the approval. The ADR-090 view shows no requester or field while locked, so the person
  cannot tell the difference. Rated P1 rather than P0 only because the keying is a disclosed known risk; a reviewer
  could reasonably call it an approval bypass (P0).
- **Confidence:** high.

### P1-2 · "Every node has its own 2FA gate" — false security claim in the release README

- **Where:** `v2/README.md:52` ("Every node has its **own encryption key**, its own notes, its own 2FA gate, its own
  agent scope"); same sentence in `v2/docs/01_CONCEPT.md:73`.
- **Evidence:** there is one gate (`GATE_SCOPE_VAULT`); `second_factor_gate` (`ops.rs:188-219`) checks only
  `is_gate_confirmed(GATE_SCOPE_VAULT)` and a vault-wide elevation. ADR-093 item 3 and K-11 say the per-node secret is
  deferred to 2.0.0 and that a code given for one node opens every node for every caller for 300 s.
- **Why it matters:** the front-page description of the security model contradicts the stamped known risk K-11.
- **Confidence:** high (code + the project's own ADR).

### P2-4 · `privateNames` can be defeated by a name-existence oracle — reproduced

- **Repro** (`python3 -I $S/s4_private.py`): owner sets `privateNames: true` on `p` and creates `STRIPE_LIVE_KEY`,
  `AWS_ROOT`, `DB_PASSWORD`. A tokenless agent in `p`'s directory: `entry.list` → `{"ids":[],"names":[],"nameHidden":true,"count":3}`,
  `search` → `[]`; then `entry.create {name:"STRIPE_LIVE_KEY"}` → `entry_exists`; `"stripe_live_key"` → `entry_exists`
  (canonical fold); `"NOT_THERE"` → created.
- **Why it matters:** an agent with `create` (the default `read-write`) confirms guessed hidden names (case- and
  look-alike-insensitively). Names only, no values, and a miss leaves an entry behind; ADR-083 enumerates the surfaces
  that withhold names but not this one.
- **Confidence:** high.

### P2-5 · `credmgr backup` has no restore path and is not a full backup — by code reading

- `v2/crates/store/src/backup.rs:61-120` packs entry envelopes, manifests, registry, root wraps, node keys and the orphan
  key; it leaves out notes (`notes.env`), sealed-node archives (`archive/<id>/`), removed-entry/undo archives, rotation
  history and the state directory's generation counter (without which a load is refused, K-8). Nothing shipped reads a
  backup file: `maintenance.doctor --rebuild-registry` (the only consumer) answers `presence_required`, and
  `scripts/emergency-decrypt.mjs` reads a vault folder (no `backup` in it). ADR-054 (`14_DECISIONS.md:1646`) calls the
  file "restorable with only the passphrase". `RELEASE.md:55` tells users "Before you upgrade, make a backup".
- **Workaround:** the same line also says to copy the vault and state directories, which is the real backup.
- **Confidence:** medium-high (not exercised end to end; there is nothing to exercise it with).

### P0-1 — the direct door is closed; the seed still leaves through two others (NOT FIXED)

Closed (reproduced as fixed, `s5`): `entry.reveal` with and without `fieldIds`, for the owner and a tokenless agent, for
a two-field entry, a one-field seed and an `otpauth://` URI, answers `value: null, redacted: "totp_seed"`; the approval
path returns no seed; `entry.create`, `entry.create_batch`, `field.update`, `entry.undo` answers carry no seed; the
seed is in neither the daemon log nor the clear on disk; the CLI has no other reveal path (`get` is the only caller of
`entry.reveal`); the bridge's `entry_copy` refuses a null value. The redaction is decided by `is_seed` =
`effective_type == TotpSeed` (`entry_doc.rs:519-522`), and that is the weakness: `totp.code` does **not** use that test.

**NEW-P0-a · An agent retypes the seed field, then reads it (reproduced on the shipped binaries, socket and MCP).**
`field.update` (and `entry.update` with `fields`) accept a `type` override from any caller holding `update`, which a
default (`read-write`) tokenless agent and the MCP tool `credmgr_field_update` have. After the override the field's
effective type is no longer `totp-seed`, so `reveal_json` returns it, while `totp.code {field}` still computes codes
from it (`select_totp_field`, `entry_doc.rs:553-563`, takes a named field of any type). `s5` (socket) and `s7` (MCP):
```
agent field.update {field: <seed>, patch: {type: "password"}}  → ok (answer has no seed)
agent entry.reveal {fieldIds: [<seed>]}                         → has seed: True | type: password
agent totp.code {field: <seed>}                                 → ok, code 408266   (the broker still uses it as a seed)
otpauth entry, patch {type: "text"}                             → reveal has seed: True
MCP: credmgr_field_update {patch:{type:"password"}}, then credmgr_get → id 3 has seed: True
owner's entry.get hasTotp: True before → False after         (the owner's 2FA marker silently disappears)
```

**NEW-P0-b · Common seed formats are not inferred as seeds but `totp.code` accepts them (reproduced on the shipped binaries).**
`looks_like_totp_seed` (`core/src/inference.rs:84-94`) accepts only `otpauth://` or exactly 16/26/32 upper-case
base32 characters; `totp.code` accepts lower case, grouping with spaces, padding and other lengths (as `07 §6`
documents). A one-field entry is used by `totp.code` without a `field` param. `s8`, owner stores each form, a tokenless agent asks:
```
lowercase                totp.code ok=True | agent reveal returns it=True | type=text
grouped (Google style)   totp.code ok=True | agent reveal returns it=True | type=text
padded 15-byte (24 ch)   totp.code ok=True | agent reveal returns it=True | type=text
32-byte (52 chars)       totp.code ok=True | agent reveal returns it=True | type=text
16 upper-case chars      totp.code ok=True | agent reveal returns it=False | type=totp-seed
```
The lower-case grouped form is what many services display as the "can't scan? enter this key" text, so this is the
ordinary case, not a contrived one. In both bypasses the broker itself treats the value as a seed (it computes codes
from it), so by the coordinator's criterion they are bypasses. `PHASE8_AUDIT_REPORT.md` §7 ("the documents that said
'never a seed' are now true") and ADR-094 item 1 are therefore not yet true. A fix needs one predicate for both doors
(reveal withholds whatever `totp.code` would accept as a seed, or `totp.code` refuses whatever reveal returns) and a
type override that cannot move a field out of the seed class without presence (or without the owner).

### P1-1 — FIXED; one NEW P2

`s6` (debug build of `db50446`): B (tokenless, cwd `p/sub`) is **not** served A's approval — it gets its own
`approval_pending`; A asking without `fieldIds` after a one-field approval → `malformed_request` ("that approval was given
for other fields…") and the approval stays; A asking for the other field → `malformed_request`. No other op reads a
staged document (`with_approved` has one caller). Residual, disclosed in K-7: another process in the *same* cwd with no
token is the same requester (`bound_workdir` is the live cwd, so any same-user process can `chdir` there).

**NEW-P2-a · A requester can evict other requesters' pending requests and bury the Lock screen (reproduced).** The request
key includes the live cwd, so an agent mints a fresh requester per subdirectory of its own work folder. `s6`: victim's
request from `p/sub`, then 520 reveals of the same entry from `W/f1 … W/f520` (0.1 s): `vault.approval_get` lists 512
rows, **victim still listed: False**, deciding the victim's id → `not_found`; `vault.status` → `pendingApprovals: 512`; every
row is identical (`entry.reveal`, same node and entry, `state: pending`) and, on a locked vault, carries no requester or
cwd, so the person cannot tell whose request they approve. Bound: the flooder must already be able to reveal that entry
(nothing is released without a decision), the cap holds memory at 512 slots, and the victim's retry makes a new request.
Effect: denial of the approval flow and decision confusion. Suggested: cap slots per (node, entry) or per scope node,
and show a requester label while locked.
